# CI/CD status

`.github/workflows/ci.yml` installs the hash-locked requirements, runs `pip-audit` and Bandit, checks Ruff lint/format, strictly type-checks the validated configuration and schema boundary modules, syntax-checks the static JavaScript, checks committed OpenAPI drift, and runs pytest with a 75% coverage floor measured against the current 78.45% local baseline. `.github/workflows/integration.yml` starts a separate, digest-pinned PostgreSQL/AGE, OpenSearch, Redis, and MinIO stack with fake credentials and throwaway volumes, then runs service tests and removes only that workflow's project. Local `make integration` follows the same isolated-stack model.

`.github/workflows/security.yml` runs CodeQL for Python and JavaScript/TypeScript plus full-history Gitleaks scanning. The third-party actions in the changed workflows are pinned to immutable SHAs, checkout does not persist credentials, and the default token scope is read-only except CodeQL's job-level `security-events: write`. Existing open Dependabot PRs still need separate review.

The docs workflow builds strict Zensical output and renders every Mermaid block with a digest-pinned Mermaid CLI image on every pull request, avoiding path-filtered missing check statuses. On `main`, it uploads and deploys the Pages artifact only when `PAGES_DEPLOYMENT_ENABLED=true`. To publish safely, an owner must first protect `main`, set **Settings → Pages → Build and deployment → Source** to **GitHub Actions**, then add that repository Actions variable. These settings were not changed during recovery. The Pages API and branch-protection endpoint currently return 404, so publication from a verified protected branch is not yet enabled.

`.github/workflows/container.yml` starts and checks a clean development service stack on an ephemeral runner, builds and smoke-tests the non-root API preview without publishing, verifies AMD64/ARM64 OCI output, scans source and image, and uploads per-platform SBOMs. `.github/workflows/release.yml` is manually dispatched: a non-publishing candidate is the default; publishing requires a matching semantic-version tag, successful named checks on that commit, ancestry from `main`, `RELEASE_PUBLISH_ENABLED=true`, and approval in the `release` environment. It promotes the already-scanned OCI archive, signs its digest with Sigstore, creates GitHub provenance and a digest-addressed GitHub Release. Those publish settings are not configured; actual publishing remains unavailable. See [release procedure](release.md) and [environment model](environments.md).

The repository is public with `main` as its default branch. The branch protection API returned 404 (“Branch not protected”), the rulesets list was empty, and Pages is not enabled. No GitHub settings were changed. An owner must configure protected `main`, Pages source, the `release` environment with required reviewers, and the `PAGES_DEPLOYMENT_ENABLED`/`RELEASE_PUBLISH_ENABLED` variables. Because this appears to be a solo-maintainer repository, do not require an independent review from a person who cannot be available; keep admin bypass and required-review policy deliberate. No license allowlist has been approved; SBOMs and license reports provide visibility until maintainers set distribution policy.
